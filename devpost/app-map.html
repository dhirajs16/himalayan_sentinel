From a source record
to evidence someone can inspect.

This offline guide follows the implemented data integrations. Static lake inventories and historical events provide context; current weather is a forecast. A person still reviews and approves each demonstration notice.

Source snapshot: implementation commit acd354d, 19 October 2026. Paths and symbols reference the finished code. This is a reference route, not a claim that a learner completed a hands-on tour. Code can change after this snapshot.

Follow one action: inspect district evidence

  1. 1 · Prepare real source recordsbackend/app/context_data.py
    import_context · ContextStore.population

    The importer chooses the latest historical revision and preserves original IDs. Population masks select valid pixel centres within a district, without labelling the result as exposure.

  2. 2 · Request a bounded viewbackend/app/context_api.py
    lakes · events · population

    The API filters the prepared records and returns a page with its total. Missing files and absent values remain explicit. The public API does not expose private citizen evidence.

  3. 3 · Inspect the resultfrontend/components/evidence-explorer.tsx
    EvidenceExplorer · useContextResource

    The browser displays the map, searchable list, retained attributes and source dates. Obsolete responses cannot overwrite the newly selected district's panels.

How a live forecast stays traceable

backend/app/district_weather.py → district_weather locates a district and requests its forecast. backend/app/providers.py → WeatherProvider.fetch coordinates concurrent requests and checks the persisted cache. The weather_observations table retains successful values and retrieval time.

A disabled provider cannot reuse a fresh live cache. A failed refresh returns a labelled stale cache or simulated fixture. backend/app/jobs.py → sync_weather selects today's Nepal date rather than blindly using the first cached day.

To change this, start here

Search fields or result paging

Change ContextStore.query in context_data.py and the filters in evidence-explorer.tsx. Keep API bounds, filter totals and displayed records consistent. Verify with backend/tests/test_context_data.py and frontend/tests/evidence.spec.ts.

Source labels and visible layout

Source metadata comes from ContextStore.catalog. Record cards and forecast/population panels are in evidence-explorer.tsx; layout is in evidence-explorer.css. A harmless label edit is an optional practice; refresh the browser and check mobile layout.

Forecast freshness or failure behavior

Start at WeatherProvider._fetch. Keep retrieval time, forecast date and simulated/cached/live modes distinct. backend/tests/test_live_weather.py covers cache disabling, concurrency, malformed data and Nepal midnight.

Notice permissions and review

Start at backend/app/workflow.py → transition_alert and frontend/components/operations.tsx. Keep jurisdiction checks, approval invalidation and version history on the server. Geographic context never establishes that a lake caused a report.

A practice to reuse

Specify what evidence would prove a source works before connecting its label to a screen. Here, devpost/prd.md → Current Weather requires a genuine successful fetch and visible timestamps; test_live_weather.py proves a cache cannot silently switch source modes. The live verification command separately checks the actual external service. A mock test and a successful external request answer different questions.

Run it again

From the repository root, after installing the documented dependencies:

./scripts/dev.ps1

Open the Rasuwa evidence explorer. The helper prepares local context, starts the API and weather worker, and runs the frontend. Private configuration stays in the ignored root .env. Detailed alternatives are in README.md.

No network is required to read this guide. Opening the running application or external map tiles requires their normal services. Submission video, public repository access and the final entry remain separate tasks.
